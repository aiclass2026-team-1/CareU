# Care U｜網站流程說明

> 文件用途：作為 Care U 後續前端框架化、模組化、Routing、State、Mock API 與前後端整合時的網站流程基準。  
> 對應流程圖：`CareU_網站流程圖.png`  
> 狀態：目前流程定稿版  
> 注意：本文件描述的是「預期網站流程與互動邏輯」，不代表目前 Prototype 已具備正式後端能力。

---

## 1. 流程圖圖例

目前流程圖以顏色與線條區分不同類型：

- **藍色框**：主要頁面
- **橘色框**：Loading／分析等待頁
- **綠色框**：Modal／視窗元件
- **藍色實線**：主要頁面流程、條件分支或返回流程
- **藍色虛線**：非必經的登入功能流程
- **綠色虛線文字**：登入成功後的返回規則說明

其中：

- `排除視窗` 為 Modal，不是獨立 Route。
- `登入視窗` 為共用 Login Modal，不是獨立登入頁。
- Login Modal 未來應可由不同頁面共同呼叫。

## 2. 整體網站主要流程

```text
入口頁
  ↓
首頁
  ├─ 有體檢資料
  │    ↓
  │  上傳體檢資料
  │    ↓
  │  Loading頁-1
  │    ├─ 資料可使用
  │    │    ↓
  │    │  問卷頁
  │    │
  │    └─ 資料不符合需求／無法讀取
  │         ↓
  │       排除視窗
  │         ↓
  │       返回首頁
  │
  ├─ 沒有體檢資料
  │    ↓
  │  直接進行問卷
  │    ↓
  │  問卷頁
  │
  └─ 開啟登入視窗
       ↓
     Login Modal
       ↓
     登入成功後返回原呼叫頁面

問卷頁
  ↓
Loading頁-2
  ↓
報告頁
  └─ 若需要查看會員內容
       ↓
     開啟登入視窗
       ↓
     Login Modal
       ↓
     登入成功後返回報告頁並解鎖會員內容
```

---

## 3. 各頁面與視窗角色

### 3.1 入口頁

用途：

- 作為 Care U 網站的品牌進場頁。
- 完成品牌動畫後轉入首頁。
- 目前不承擔會員登入、資料上傳或分析功能。

主要流程：

```text
入口頁 → 首頁
```

---

### 3.2 首頁

首頁是整個網站的主要分流入口。

目前有三種主要行為：

#### A. 使用者有體檢資料

使用者選擇上傳體檢資料：

```text
首頁
→ 上傳體檢資料
→ Loading頁-1
```

上傳檔案目前預計支援 PDF、JPG、PNG 等格式；正式限制需在後續前後端規格階段確認。

#### B. 使用者沒有體檢資料

使用者可直接從首頁進入問卷：

```text
首頁
→ 問卷頁
```

此流程不經過 Loading頁-1。

#### C. 使用者進行登入

首頁可呼叫共用的 Login Modal：

```text
首頁
→ 開啟登入視窗
→ Login Modal
```

登入成功後：

```text
Login Modal
→ 返回首頁
```

目前不製作「首頁登入後的專屬畫面」。

---

## 4. Loading頁-1

### 4.1 主要用途

Loading頁-1 位於「上傳體檢資料」之後。

概念上負責：

- 讀取使用者上傳的資料
- 判斷資料是否符合需求
- 整理可使用的健康資訊
- 判斷哪些資訊已存在
- 判斷後續問卷需要補充哪些資料

目前 Prototype 僅模擬上述流程，不代表已串接正式 OCR、AI、RAG、資料庫或分析服務。

### 4.2 正常流程

當資料可使用時：

```text
Loading頁-1
→ 問卷補足資訊
→ 問卷頁
```

### 4.3 異常流程

當資料：

- 不符合系統需求
- 無法讀取
- 或其他後續正式系統定義的不可處理狀態

則：

```text
Loading頁-1
→ 排除視窗
```

---

## 5. 排除視窗

`排除視窗` 是 Modal／狀態視窗，不是獨立頁面。

用途：

- 告知使用者目前上傳的資料無法繼續處理。
- 提供返回首頁並重新開始的操作。

流程：

```text
Loading頁-1
→ 排除視窗
→ 返回首頁
```

目前流程圖以「資料不符合需求／無法讀取」作為主要觸發概念。

正式系統後續可再依 API / Backend Error Code 細分，例如：

- 檔案格式不支援
- 檔案無法解析
- 非目標健康資料
- 資料內容不足
- 系統處理失敗

但在目前 Prototype 與流程圖階段，不先自行定義正式錯誤碼。

---

## 6. 問卷頁

問卷頁有兩種進入來源。

### 6.1 有體檢資料

```text
首頁
→ 上傳體檢資料
→ Loading頁-1
→ 問卷頁
```

此時系統預期已取得部分健康資料，因此問卷主要用來：

- 補足缺少資訊
- 蒐集健檢資料中不存在的內容
- 依資料狀況決定需呈現的題目

### 6.2 沒有體檢資料

```text
首頁
→ 問卷頁
```

此時系統沒有前置健檢資料，因此需要蒐集較完整的基本資訊與健康相關問卷資料。

### 6.3 問卷完成後

兩種來源最後皆匯流到：

```text
問卷頁
→ Loading頁-2
```

---

## 7. Loading頁-2

### 7.1 主要用途

Loading頁-2 位於問卷完成之後。

與 Loading頁-1 的角色不同。

#### Loading頁-1

重點是：

```text
讀取體檢資料
→ 判斷資料可用性
→ 找出缺少資訊
→ 準備補充問卷
```

#### Loading頁-2

重點是：

```text
整合所有已取得資料
→ 進行分析
→ 整理保健關注方向
→ 準備個人化報告
```

目前 Prototype 僅模擬上述狀態，不代表正式分析服務已建立。

### 7.2 完成後

```text
Loading頁-2
→ 報告頁
```

---

## 8. 報告頁

報告頁承接 Loading頁-2 的分析結果。

目前規劃包含：

- 健康／保健關注分析摘要
- 保健關注優先度
- 個人化分析結果
- 部分免費內容
- 會員專屬完整內容
- 保健食品候選推薦
- 專屬保健組合

### 8.1 未登入狀態

使用者仍可先閱讀部分報告內容。

部分會員專屬內容會保持鎖定。

目前規劃：

- 第一、第二名保健關注方向需登入後解鎖
- 從保健食品推薦區域開始，主要內容屬會員專屬

### 8.2 會員內容解鎖

當使用者需要查看會員內容：

```text
報告頁
→ 會員內容解鎖
→ 開啟 Login Modal
```

Login Modal 並不是報告頁之後的必經下一頁。

它只在使用者主動要求解鎖會員內容時被呼叫。

登入成功後：

```text
Login Modal
→ 返回原報告頁
→ 解鎖會員內容
```

不重新執行：

- 問卷
- Loading頁-2
- 報告分析流程

並應盡量保留使用者原本的報告閱讀位置與操作狀態。

---

## 9. 登入視窗（Login Modal）

### 9.1 定位

登入功能採共用 Modal 設計，而不是獨立「登入頁」。

未來可由：

- 首頁
- 報告頁
- 其他需要會員權限的功能

共同呼叫。

### 9.2 呼叫來源

#### 從首頁開啟

```text
首頁
→ Login Modal
→ 登入成功
→ 返回首頁
```

目前不製作首頁登入後的會員專屬畫面。

#### 從報告頁開啟

```text
報告頁
→ Login Modal
→ 登入成功
→ 返回報告頁
→ 解鎖會員內容
```

### 9.3 工程化原則

正式工程化後，Login Modal 應作為共用元件處理。

登入成功後的行為應根據「呼叫來源」決定，而不是在 Login Modal 內將返回頁面寫死。

概念上需要保留：

```text
returnTo / caller / postLoginAction
```

之類的狀態。

具體欄位與實作方式留待 Vue / Router / Pinia / Auth 架構階段確認。

---

## 10. Flow 中「頁面」與「視窗」的差異

### 頁面／Route 候選

目前主要頁面包含：

- 入口頁
- 首頁
- Loading頁-1
- 問卷頁
- Loading頁-2
- 報告頁

正式 Route 命名將在 Vue Router 階段確認。

### Modal／非獨立 Route

目前包含：

- 排除視窗
- 登入視窗 Login Modal

兩者原則上不需要因為開啟視窗而離開目前主頁面 Route。

---

## 11. Prototype 與正式系統的區分

目前已完成或製作中的 HTML 皆屬 Prototype。

因此流程中的：

- Loading 時間
- Demo Controller
- 假登入
- 假分析結果
- 假商品
- 假分數
- setTimeout
- 前端模擬錯誤
- 模擬會員解鎖

都不得直接視為正式系統邏輯。

後續工程化時應保留：

```text
使用者體驗與畫面邏輯
```

但正式資料流應逐步改為：

```text
Vue App
→ State
→ Service Layer
→ Mock API
→ API Contract
→ Real Backend
```

---

## 12. 後續工程化時的流程檢查重點

Technical PM / AI Agent 在 Frontend Migration Audit 與 Routing 階段應確認：

1. Prototype 的實際跳轉是否與本流程文件一致。
2. 是否有 Prototype Demo 行為被誤認為正式 Route。
3. 排除視窗是否保持 Modal，而非獨立頁面。
4. Login Modal 是否保持共用元件，而非獨立登入頁。
5. 首頁與報告頁是否能呼叫同一套 Login Modal。
6. Login 成功後是否返回原呼叫頁面。
7. 報告頁登入成功後是否直接解鎖，而不重新跑分析。
8. 有健檢與無健檢兩條流程是否能正確匯流至問卷與 Loading頁-2。
9. Loading頁-1 與 Loading頁-2 的責任是否保持分離。
10. 排除流程是否能正確返回首頁。
11. Browser Back / Forward / Refresh / Direct URL 行為需在 Router 階段另外確認。

---

## 13. 目前不在本流程圖中定案的內容

以下項目目前不由這份網站流程圖決定：

- 正式 Route Path
- API Endpoint
- DB Schema
- OCR Provider
- AI / LLM Provider
- RAG 架構
- Auth Token / Session 方式
- Priority Score 正式計算公式
- 正式推薦演算法
- 商品庫存
- 正式購物車 API
- 金流
- 部署平台

上述內容應在後續對應 Phase 再確認，不應由 AI Agent 因流程圖內容自行推斷。

## 14. 流程基準摘要

目前 Care U 的核心使用者流程可簡化為：

```text
入口頁
↓
首頁
↓
有體檢資料？ ──────────────┐
│                          │
是                         否
↓                          ↓
上傳體檢資料               直接問卷
↓                          │
Loading頁-1                │
├─ 可使用 → 問卷頁 ←───────┘
└─ 不符／無法讀取
       ↓
     排除視窗
       ↓
      首頁

問卷頁
↓
Loading頁-2
↓
報告頁
↓
需要會員內容時
↓
Login Modal
↓
登入成功返回報告頁並解鎖
```

另外，首頁亦可隨時呼叫共用 Login Modal。
